Home Lab

Le bon objectif : créer un portfolio de preuves, pas une collection d’outils

Pour renforcer votre profil, votre homelab doit démontrer une chaîne complète :

Cartographier → évaluer les risques → sécuriser → superviser → détecter → investiguer → documenter

Compte tenu de votre expérience à la Banque de France, de votre expertise en analyse des risques et de votre pratique de Python, je vous conseille un homelab orienté Blue Team / SOC / GRC, plutôt qu’un laboratoire centré uniquement sur le pentest.

Votre avantage différenciant serait de montrer que vous savez relier :

les risques métier ; l’architecture technique ; les mesures de sécurité ; les événements observés ; les décisions de remédiation ; les indicateurs destinés au management. 1. Segmentation minimale VLAN 10 — Management

Contient exclusivement :

l’interface d’administration Proxmox ; le serveur de supervision ; les interfaces de gestion ; éventuellement un bastion d’administration.

Seul votre poste d’administration doit pouvoir atteindre ce réseau.

VLAN 20 — Serveurs

Contient :

un serveur Linux ; une application web de démonstration ; une base de données ; éventuellement un contrôleur de domaine dans une seconde phase. VLAN 30 — Utilisateurs

Contient :

un poste Windows ; un poste Linux ou Ubuntu Desktop ; les agents de collecte et de supervision. VLAN 40 — Laboratoire isolé

Ce réseau sert exclusivement aux exercices autorisés sur vos propres machines :

tests de configuration ; génération contrôlée d’événements ; validation de règles de détection ; restauration après incident ; tests de segmentation.

Il ne doit pas avoir de route directe vers votre réseau familial, vos équipements personnels, vos données réelles ou Internet, sauf accès sortant temporaire et strictement contrôlé pour les mises à jour. Proxmox permet de travailler avec des réseaux virtuels, son pare-feu et des fonctions SDN adaptées à cette séparation.

  1. Commencer par une plateforme raisonnable

Ne déployez pas simultanément Wazuh, Security Onion, Splunk, TheHive, MISP, Grafana et plusieurs EDR. Vous produiriez une architecture impressionnante mais difficile à comprendre et à maintenir.

Phase initiale : Wazuh

Je commencerais par Wazuh en installation mono-nœud. Sa documentation officielle couvre notamment :

la collecte par agents ; l’analyse des événements ; la surveillance d’intégrité des fichiers ; l’évaluation des configurations de sécurité ; la détection de vulnérabilités ; le suivi de Docker ; l’intégration d’un IDS réseau ; les déploiements en VM ou Docker ; les cas d’usage de conformité.

Cela vous permettra d’utiliser honnêtement dans votre CV des expressions comme :

déploiement d’un SIEM ; collecte centralisée des journaux ; supervision d’endpoints Windows et Linux ; File Integrity Monitoring ; détection de vulnérabilités ; investigation d’alertes ; création et ajustement de règles ; tableaux de bord de sécurité. Phase ultérieure : Security Onion

Security Onion est pertinent lorsque vous voudrez approfondir la visibilité réseau. La plateforme réunit notamment Suricata pour la détection par signatures, Zeek ou Suricata pour les métadonnées réseau, la capture de paquets, la visibilité des endpoints, la gestion des alertes, le threat hunting et la gestion de cas.

Mais ses besoins matériels sont sensiblement plus importants. Je ne l’ajouterais qu’après avoir parfaitement documenté le premier périmètre Wazuh.

C’est probablement le projet qui valorisera le mieux votre parcours.

What Os is best to setting up this homelab: linux or macos ?

Short answer: Linux — preferably Proxmox VE on a dedicated x86-64 machine

For the homelab we discussed, Linux is the better host platform than macOS.

My recommended setup is:

Host OS / hypervisor: Proxmox VE Hardware: dedicated Intel or AMD mini-PC/workstation Daily computer: keep using your Mac if you have one Administration: connect from macOS to Proxmox through its web interface and SSH Guest systems: Windows, Ubuntu/Debian, Wazuh, OPNsense and eventually Windows Server

Proxmox VE is based on Debian GNU/Linux and its official installer is the recommended installation method. It is designed to host KVM virtual machines and Linux containers, with integrated virtual networking, firewalling, backups and snapshots.

Why Linux/Proxmox is better 1. It better reflects enterprise infrastructure

Your objective is not merely to run a few security tools. You want to demonstrate experience with:

hypervisors; virtual machines; network segmentation; Linux administration; firewalls; Windows and Active Directory; centralised logging; SIEM deployment; snapshots and restoration; infrastructure automation.

A dedicated Proxmox host exposes you to substantially more relevant infrastructure concepts than running several desktop VMs directly from macOS.

It also gives you credible CV terminology:

Proxmox VE, Debian Linux, KVM, virtual networking, network segmentation, firewall rules, virtual machines, containers, snapshots, backup and restoration.

  1. Proxmox provides better lab networking

Your proposed homelab requires several isolated networks:

Management Servers User workstations Monitoring Isolated testing environment

Proxmox includes virtual networking, software-defined networking and host-level firewall capabilities. This makes it appropriate for modelling an enterprise-style network rather than placing every machine behind the same desktop NAT connection.

On macOS, Parallels, VMware Fusion or UTM can run VMs effectively, but complex multi-segment networking is generally less natural and less representative of a dedicated virtualisation server.

  1. You can leave it running continuously

A security-monitoring lab becomes much more useful when it operates like a small server:

Wazuh continuously receives events; scheduled scans execute automatically; dashboards retain history; systems can be updated remotely; you can observe normal activity over several days; you can practise backup and restoration.

A MacBook is less suitable as a permanent server because it is frequently suspended, transported or disconnected. A dedicated mini-PC can run quietly and independently.

macOS is still useful — as the administration workstation

This does not mean macOS is a poor operating system for cybersecurity work.

A good division of roles is:

Mac ├── Web browser → Proxmox and Wazuh dashboards ├── VS Code → documentation, Python and Ansible ├── SSH → Linux administration ├── Git → portfolio repository └── VPN → secured remote lab access

Dedicated Linux/Proxmox host ├── OPNsense ├── Wazuh ├── Ubuntu Server ├── Windows workstation ├── Windows Server / Active Directory └── Isolated test environment

This is arguably the strongest combination: macOS as your daily workstation, Linux as your laboratory infrastructure.

Important distinction: Intel Mac versus Apple Silicon If you have an Intel Mac

An Intel Mac can run x86-64 Windows and Linux virtual machines relatively naturally through a desktop hypervisor. It can therefore support an initial version of the lab.

However, I would still prefer dedicated Proxmox hardware because it offers:

more realistic networking; continuous availability; easier snapshots and backup management; independence from your personal computer; a stronger infrastructure learning experience. If you have an Apple Silicon Mac

If your Mac uses an M-series processor, the distinction is more important.

Apple Silicon uses an ARM architecture, while the official Proxmox requirements specify Intel 64 or AMD64 hardware with Intel VT or AMD-V for KVM virtualisation. Proxmox does not provide the normal supported installation path for an Apple Silicon host.

Experiments exist for running Proxmox-related packages on ARM, but they rely on unofficial builds or custom compilation and are not the clean, supported path you want for a career portfolio.

An Apple Silicon Mac can comfortably run:

ARM Linux virtual machines; Docker containers; some ARM-compatible security tools; Windows 11 for ARM.

However, you may encounter limitations with:

x86-only appliances; some prebuilt virtual-machine images; nested virtualisation; Windows Server labs; certain network-security appliances; recreating standard enterprise x86 environments.

For this reason, I would not build the main lab around an M-series Mac.

Recommended hardware Sensible starter configuration

Look for a used business mini-PC or small workstation with:

Intel Core i5/i7 or AMD Ryzen; x86-64 virtualisation support; 32 GB of RAM minimum; 64 GB preferred if you want Active Directory and Security Onion later; 1 TB NVMe SSD; one Ethernet interface minimum; two Ethernet interfaces preferred; upgradeable memory and storage.

Proxmox officially recommends an Intel 64 or AMD64 processor with hardware virtualisation, memory for the host plus the guests, SSD storage and sufficient network interfaces for the intended setup.

Hardware tiers 16 GB RAM

Suitable for a reduced lab:

OPNsense; Wazuh, with tight resources; one Linux server; one lightweight client.

It will become restrictive quickly.

32 GB RAM — recommended starting point

Suitable for:

OPNsense; Wazuh; Ubuntu Server; Windows 11; an administration or application VM. 64 GB RAM — ideal

Suitable for the above plus:

Windows Server; Active Directory; an additional Windows client; Security Onion experiments; multiple simultaneous scenarios.

Wazuh and Security Onion are memory-intensive primarily because of indexing, dashboards and log retention. Therefore, RAM is usually more important than buying the fastest processor.

Host installation

Install Proxmox VE directly on the dedicated machine, rather than:

Ubuntu Desktop with VirtualBox; macOS with several desktop VMs; Proxmox nested inside another hypervisor; Docker for every component.

Proxmox’s official documentation recommends its ISO installer for new deployments; installing Proxmox over an existing Debian system is considered the more advanced alternative.

When macOS alone is acceptable

Use macOS as the host initially if:

you do not yet want to buy equipment; your aim is to create a proof of concept; you only need two or three VMs; you are comfortable with limited network realism; you intend to migrate to Proxmox later.

In that case, start with:

macOS ├── UTM, VMware Fusion or Parallels ├── Ubuntu Server VM ├── Windows VM ├── Wazuh VM or Docker deployment └── One isolated virtual network

Treat this as phase zero, not the final architecture.

Do not spend weeks trying to reproduce an elaborate datacentre topology on macOS. Build one working Wazuh scenario, document it, and migrate to dedicated hardware when the concept is validated.

Final recommendation Situation Best choiceYou want the strongest career portfolio Dedicated x86-64 host with Proxmox VE You already own an M-series Mac Use it as the admin workstation, not the principal hypervisor You own an Intel Mac and have no other hardware Acceptable for an initial proof of concept You want Active Directory, realistic networking and SIEM monitoring Proxmox VE You only want Python, Docker and one Linux VM macOS is sufficient You want a lab running continuously Dedicated Linux/Proxmox host

Therefore: choose Linux for the homelab host, specifically Proxmox VE. Keep macOS as your development, documentation and administration workstation.
